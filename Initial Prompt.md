# Goal

I have a customer that needs to develop a real time customer segmentation solution.
The architecture has customer events being generated by multiple customer sessions in the ecommerce website, that are sent to GCP Dataflow and then to GCP Pub/Sub. From Pub/Sub, there's another Dataflow pipeline that needs to be created, that needs to create the customer segmentations.

Below are the main requirements of the solution

# Requirements

- Baseline traffic: 4 k messages/second
- Spikes in traffic within seconds e.g. campaign starts - > up to 8k /s
- Overall latency from raw tracking event till personalization result is available in " Customer 360 API"  < 2 seconds
- Session window  needs to be opened for every visitor -  Challenges:
    - When to end a session? There is often no clear " end"  signal
    - There are session w ith 500+ single events -  we can' t keep everything in memory
    - We need to keep the right order of events available for lookup because of the definition of segments - > e.g. visitor needs to open a product page, aftertwards do a search and land on a campaign page -  exactly in this order he's put in a specific segment
    - Tracking events need to be also aggregated e.g. How  many product views happend in this session till now, how  many searches
    - We also need to track timing between the events e.g. how  much time spend the customer on a specifc product page
    - We want to start with a rule based segmentation identification but already want to prepare to use a ML model to detect the current segment which means we need to be extremely efficient in feature engineering to serve the model with the right data format
    - We will use also historical information to extend the information for a current session e.g. which was the last segment the visitor was put into in his last session
    
#Segments definition:
- Segments are defined by UX / Business units and they are basically describing how a customer needs to behave on the webshop to be put into a specific segment -  it' s static rules (at the moment)
- They are consinously evolving -  we need to have a flexible setup to adjust the "rules"

# Solution
I still don't have a finished solution of how the architecture and pipeline should look like, so I need your help for finding it and challenging me in the points I consider below as being the possible approach.

The document `architecture-overview.md` should be considered for its layout, but I want to start from zero to think about the archicture.

The flow starts by Dataflow receiving an event from the Pub/Sub. There will be a validation on the schema of the event. Then it's important to group the events by key, which will make it possible to parallelize the flow. After this the main DoFn will be executed.
Let's start from the zero, where no events for a specific key has already come. The system needs to query MongoDB to validate if a session is already available for that key. Let's start with the case that there isn't any session.
The function will instantiate a new ValueState to create the session.
It's also important to load the segmentation rules in that function. The rules will be discussed afterwards, but this should be a Side Input that get's the rule set from MongoDB as well and make it available to multiple DoFns.
In paralel there's also another ValueState with counts on the number of events happening of specific types, like product views and searches.
When the events come in, the DoFn will add the event to the orderedListValue. The stateful DoFn will always add to this orderedList. Another value will be added to count the number of elements inside the orderedList. If the number of elements are greater than N (50 for instance), the system should remove the oldest element from the list, keeping the number of elements always below the max. For every new event, the system will validate if the 50 ordered elements within the list match any of the rules.
If the rule is matched, the session value gets updated with the segment and the pipeline moves forward to send the segmentation to another Pub/Sub topic.
If the rule isn't matched, the DoFn will update the session with the latest information and counters.
In parallel, there should be a Timer that gets updated everytime a new event comes in for a specific sessionKey. A trigger should be activated everytime no events for a session haven't come with X minutes (10min for instance). When the trigger is activated, the system will send a request do MongoDB saving the session information long-term and erase the states, in this order. The session has all important information, such as state variables, counts and list of last X events.
The next event that comes in for that session, could it be in a few days, will be able to retrieve that session and continue the process.
As for the side input, the rule set will be stored in MongoDB. Everytime the rule set is updated, which could be by using MongoDB Change Streams, a new event is generated and the rules are updated automatically.
When they want to implement ML to detect the segments, this can also be applied in this flow, overwriting the rule validation by sending the events to a RunInference method down the pipeline

What I'm mostly concerned is with the memory consumption of the flow. We need to come up with a solution that allows when a session aggregation becomes too large, to offload it to the database. Remember that the main goal of the solution is to find which segment a customer is associated based on the event stream. The event stream might not be ordered, so we need to make sure to order the events for comparison.
Also, another important point is that the rules for segmentation must be set in a way that they can be flexible, so they can be easily adjusted, as they are consinously evolving.
